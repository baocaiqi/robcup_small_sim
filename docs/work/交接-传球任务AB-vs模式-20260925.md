## 2 怎么跑的（vs 模式 · 同种子 · 同档 · K≥200）

### 2.1 通道 = farm 的 `vs` 模式

`run_farm.sh` 的 vs 分支：给 `STRAT_BLUE=<树A> STRAT_YELLOW=<树B>` ⇒ 引擎各编一个 `.so`、**两份源码树对打**，
产物落 `build/farm/out_vs[_<后缀>]/`（含 `vs.csv` 逐局原始行、`_manifest.json`、`reflog/`、`vs_table.txt`），
并强制跑 `farm/vs_selfcheck.py`（独立重算两棵树的 sig，抓"谁跟谁打"弄反）—— **不合格即拒绝出产物**。

### 2.2 四格设计（同 `seed0=1000` / 同档 `no-referee/whos=rel` / 同 `frames=18000`，**逐局按 seed 配对**）

| 格 | 蓝侧 | 黄侧 | K | 用途 |
|---|---|---|---|---|
| `c1` | A 传球开 | B 传球关 | 2000 | 语境①「对手恒为 B」的基线 |
| `c2` | B 传球关 | A 传球开 | 2000 | 语境②「对手恒为 A」的候选 |
| `c3` | A 传球开 | A 传球开 | 2000 | 自对打 = **镜像探针**（语境②基线） |
| `c4` | B 传球关 | B 传球关 | 2000 | 自对打 = **镜像探针**（语境①候选） |
| `rlg_c1` / `rlg_c4` | 同 c1 / c4 | 同 c1 / c4 | 200 | **逐局 rlg**，供门区指标从帧级位置复算 |

由这四格得到 **3 类干净的因果量**：

```
① 对手固定为 B： Δ1 = c4 − c1     （蓝侧 关闭−开启；对手黄恒为 B）
② 对手固定为 A： Δ2 = c2 − c3     （蓝侧 关闭−开启；对手黄恒为 A）
③ 头对头净胜：  (c2.net − c1.net)/2 = t_B − t_A
   推导：蓝侧有偏置 s 时 c1.net = t_A − t_B + 2s、c2.net = t_B − t_A + 2s ⇒ 相减把 s 消掉
```

**为什么要这样设计**：vs 模式两队的**边（蓝/黄）不是对称的**（见 §5 镜像探针：自对打时蓝侧触球仍多于黄侧）。
只跑一个方向会把"边偏置"读成"改动效果"。上面 ① 把对手钉死、② 换语境复核、③ 用相减把边偏置构造性消掉 —— 三者互为独立复核。

### 2.3 统计口径（与 farm 一致）

```
Δ_i = 观测量(候选, 第 i 局) − 观测量(基线, 第 i 局)        # 同 seed 逐局配对
CI  = 配对 Δ 的 percentile bootstrap（抽样单位 = 局，B=10000，定种 seed=20260919）
MDE = 2.802·sd(Δ)/√K                                       # 噪声地板
判定：CI 完全 >0 / <0 ⇒ 更好 / 更差；跨 0 ⇒ 本档不可分辨
```
每个 Δ 另给**正态近似 CI**做交叉验证（两者在全部指标上一致到小数点后 2 位）。

### 2.4 为什么是并行跑的（留给接手人）

`run_farm.sh` 的并行度是**按变体**（`xargs -P JOBS`），而 vs 模式只有 1 个"变体"⇒ **单进程**，
本机实测 ≈1.3–1.6 s/局 ⇒ 4×2000 串行要好几小时。
`driver_vs_par.sh` 的做法：**每格一个独立引擎副本**（`/tmp/vsrun/<格>`）⇒ 6 格真正并行，
**每格内部仍原样走 `run_farm.sh`**（自检、盖戳、对比表一步不减），只把目录隔离。整批墙钟约 37 分钟。

## 8 边界：这份材料**不能**说什么（引用结论时必须一起引）

1. **不能回答「我们打得过官方 demo 吗」** —— 本台的对手是**我们自己的 baseline 策略**，
   magic 只能回答「同一对手、同一档下，A 是否比 B 好」（`engine/farm/README.md` 适用边界）。
2. **自研引擎比分永不对外**；这里的一切只用于引擎侧粗筛，**官方平台 oracle 必须另采**，本轮未做真机验证。
3. **`referee` 档的比分建在一个近乎退化的仪器上**（引擎侧已登记的未决项，不是我引入的）：
   镜像局 **95.7% 是 0:0**、镜像触球帧仅 845.8/局（默认档是 7547/局，**少 9 倍**）、
   每半场约 **190 条**判罚事件（每 1.6 s 一次重启）、其中 `FreeBall LeftBot` **91 次/局**
   （官方语料里 `LeftBot` 出现 **0** 次）。⇒ **§6.2 的 −0.49 只在该仪器内成立**，能否外推本材料不判断。
4. **默认档噪声大**（sd(Δnet)≈1.75，MDE 0.110 球/局 @K=2000）⇒ 只适合分辨大口径改动；
   `➖ 不可分辨` 的含义是「**本档看不出来**」，**不是**「没有差别」。
5. **接触物理是拟订值**（L2b 接触保真度 F1≈0.368，球↔机器人动量传递半径 +1.0 cm 就能翻转个别判定）
   ⇒ 对「接近球的距离」类改动**偏保守**。
6. **门区两条尺子分岔未裁定**（§3.3）：`own_box` 说关闭更差、`opp_box` 单人滞留说关闭更好，
   而 referee 档的真实判罚与 `own_box` 同向 ⇒ **引擎判罚触发点与几何尺子的对应关系未查清**，只登记。
7. 本轮**只测了一个字面量**（`kPassTasksEnabled` 0/1 两档），**没有**做剂量-反应、也没拆开关。

## 9 未决项 / 下一步建议（按性价比）

1. ⭐ **查清门区两条尺子的分岔**（§3.3 / §8-6）：`own_box` 与引擎实际判罚同向、`opp_box` 反向。
   若判罚确实按"防守方自己门区"触发，那与 `field_info.hpp` 注释写的 FIRA 规则（进攻方在**对方**门区）**不一致**，
   属引擎侧可能的口径 bug。**这条不查清，门区指标就只能当"几何诊断"用。**
2. ⭐ **查清 `referee` 档的仪器退化**（§8-3）：镜像 95.7% 0:0、每半场 190 次重启、`FreeBall LeftBot` 91/局。
   在它修好之前，referee 档的比分（含 −0.49）只能当"本仪器内成立"。
3. **拆开关**：`kPassTasksEnabled` 现在是**一个总开关**（A/B 差异就是这一个数）。
   关闭的代价是"进攻变钝 + 门区纪律退化"，若要"保留协作传球但不让主攻手等待"，
   需先把它拆成「发起侧 / 接应侧」两个独立开关，再各编一棵树重跑本流程 —— **本轮脚手架可直接复用**

4. **官方平台小样本验证**：magic 只能粗筛。开/关各跑若干场真机，看「输赢」与「球权」是否同向
   —— 这是唯一能回答"多赢球吗"的地方。
5. ⚠️ **不要**继续用已停用的 `sim_bench` / 其 `sim_eval_*.json`（建在已知错的 `kSpeed=0.9` 上，已登记为不可引用）。
